## 1. 验收结论

**结论：有条件通过（Conditional Pass）。**

对照需求基线与 38 项任务清单，一期范围内的功能、架构、质量与缺陷闭环均已达成，质量闸门（严过关）已就补实现给出「放行」结论，5 道门禁 tag 全部落地，静态归零门禁与对比度独立复算数据达标。据此，**主题功能本体予以验收通过**。

之所以为「有条件」而非「无条件通过」，是因为以下**验证条件尚未完成**，属环境限制导致的客观缺口，而非功能缺陷：

- 完整 App 的 `xcodebuild` 构建在本环境仍受沙盒限制（SwiftPM 包解析调用 `sandbox-exec` 被拒），已在原生 macOS 终端补跑前用临时 SwiftPM 工程做过等价的全量 iOS 27 模拟器编译（见 §5.5）；
- 像素级截图对比、Instruments 60fps 性能、20 次冷启动无闪默认色尚未执行；UI 交互冒烟已完成主链路（见 §5.5），但预设点击 / Mesh 锚点拖拽 / 5 秒撤销的逐项时序断言仍待补；
- 二期 iCloud 主题本体同步代码已就位但默认关闭、未接开关，本版不可用（已列为明确边界，非一期承诺范围）。

**放行条件**：按第 6 节《分发前补验清单》补齐剩余项目且无回归后，即可转为「无条件通过」并启动自签 / TestFlight 分发。补验责任方与时点见第 6 节。

### 5.5 补验结果（2026-11-28 追加）

**背景**：`xcodebuild` 在本环境包解析阶段报 `sandbox-exec: sandbox_apply: Operation not permitted`；改用临时 SwiftPM 工程（源码符号链接 + `swift build --disable-sandbox`，`arm64-apple-ios27.0-simulator`，Swift 5 模式，iOS 27 SDK）完成等价全量编译，再把产物打包为 `.app` 安装到 iPhone 18 Pro（iOS 27.2）模拟器。该路径绕开了 Xcode 工程包解析，未改工程配置。

**全量编译暴露并已修复的真实缺陷（此前只 typecheck Theme/ 模块，未覆盖 App 全量源码）：**

1. `Theme.swift` 六处 `.themeFont(...))` 多余右括号，语法错误；
2. `PressableStyle` 迁移到主题 ShapeSpec 后删掉了 `init(scale:)`，但 35 处调用仍传参；已补兼容初始化（默认回退 `ShapeSpec.pressScale`，显式传参仍生效）；
3. `ReaderView.swift` 阅读页 `effectiveSurface` 的 `ThemeColor` 直接当 `ShapeStyle`/`Color` 用；已统一经 `ThemeEngine.color(_:scheme:)` 转换，并补齐 `ReaderPageView` / `ScrollReaderView` / `ParagraphView` 丢失的 `theme` 环境；
4. `ReaderView` 把 `ThemeTokens.background`（`ResolvedBackground`）当颜色用于卡片与页面预览；已改读 `reader.background`；
5. `ThemeEditorViews.swift` Mesh 锚点编辑器按三维数组 `points[r][c]` 写，而模型是扁平 `[[Double]]`；已按扁平索引重写网格线、锚点渲染、拖拽与建网逻辑，并修正 `case let .mesh(points, var colors)` 的非法绑定；
6. `commentCard` 有局部变量却依赖隐式返回，补显式 `return`；`Labs.swift` 遗留 `theme.coral`（令牌不存在）改为 `theme.accent`。

**补验通过项：**

- 全量 App 源码 iOS 27 模拟器编译 `Build complete`，零错误；
- YeHangCore 93 项 / LegadoCore 55 项测试全部通过（合计 148 项，0 失败）；
- 模拟器安装并冷启动成功，书架页正常渲染，无崩溃弹窗；
- 切换内置主题（`builtin.yehang.original` → `builtin.inksea.goldhook`）后冷启动，界面由暖浅色变为深墨蓝 + 金色，持久化换肤生效；

- 系统切换深色模式无异常；运行日志仅见系统 `PointerUI` XPC 警告，无 App 崩溃 / 异常。

- **门禁驱动、逐阶段收口**：5 道门禁 tag 与 38 项任务强绑定，一任务一原子 commit，任一阶段不达标不进入下一阶段，最终可精确回退到任一稳定门禁。
- **零视觉变化起步 + 全局保险丝**：阶段 0 先验证机制、外观零差异；`backend` 三态影子写提供运行时总开关，风险可控。
- **质量三审并行且真发现问题**：测试 / 代码质量 / 根因三层审查独立产出，定位并修复 B1、D1、I1/I2/I3、缺陷 1/2、D2 等 9 类缺陷；D1 对比度从 1.22:1 修到 4.78:1，护栏经独立复算确认有效。
- **不会就先不改边界**：系统启动屏、字体 UTI、平台限制如实列边界，二期默认关闭，未把未开放能力包装成已交付。
- **验收证据量化**：对比度、归零门禁、测试套件数全部给出可复核的客观口径（区分调用点与 grep 命中行）。

### 7.2 可改进的（Improve）

- **环境验证前置不足**：完整 App 构建与真机验证拖到收尾才暴露为缺口，应在 Phase 0 就确认本机 xcodebuild / 沙盒可用性，或尽早接入可用 CI 构建机。
- **Phase 5 放行反复**：曾出具「不放行」，缺陷修复后才改判「放行」，说明补实现 4 处应在编码阶段就纳入 DoD，而非文档交付后再补。
- **二期开关留白**：`ThemeSyncService` 代码已就位却未接开关，易造成「功能是否已交付」的认知歧义，建议在代码层以编译开关或明确标注隔离。
- **残留 4 处 Palette**：虽为兼容壳 / 常量 / 内置基准，仍建议在后续版本给出清理计划或显式豁免登记，避免下轮重复盘点。

### 7.3 经验沉淀（Lessons）

- **迁移类项目先建「统一分母口径」再谈归零**：以提交树 HEAD 为准、排除 worktree、区分调用点与命中行，避免各阶段数字打架。
- **性能门禁前置不可颠倒**：MeshGradient 缓存先落地并过 Instruments，再上编辑器，避免返工。
- **对比度护栏要有可复算数据**：不能只写「已修复」，要给出 19.34 / 17.92 / 16.36:1 与边界 4.78:1 这类可复核证据。
- **数据 / 代码解耦是回退底气**：主题数据与代码分离，回退代码不损用户数据，验收与上线都更有安全感。
- **验收结论要如实分级**：功能通过但环境验证未完时，用「有条件通过 + 明确补验清单」替代简单「通过」，既不放水也不误伤交付。
