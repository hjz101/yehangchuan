## 2. 磁盘目录结构

主题**独立于** `library.json`，放在 Application Support 下：

```
Application Support/YeHangChuan/Themes/
├── themes.json                    ← 目录/索引（提交点）
├── themes.prev.json               ← 上一版索引（仅当前主索引可读时轮转）
├── themes.corrupt-<时间戳>.json    ← 主索引损坏时的留档副本（不覆盖原文件）
├── theme-decode-error.txt         ← 解码/写入失败原因（逐行追加，含 ISO8601 时间）
└── Assets/
    └── <sha256 前 32 hex>.{png,jpg,jpeg,heic,webp,ttf,otf}   ← 内容寻址资产
```

关键事实与约束：

- `themes.json` 是**唯一提交点**，内容为 `ThemeCatalog`（`schemaVersion` / `activeThemeID` / `themes` / `assets` / `skippedThemes` / `pendingDelete`）。
- 资产一律以 **SHA-256 前 32 位 hex** 命名，引用只存 `assetID`，**绝不存绝对路径 / URL**；`assetID` 必须是 32 位小写 hex（路径穿越硬防线）。
- 写入顺序：**先资产后索引**；索引 `.atomic + .sortedKeys`；`sequence` 递增防旧写覆盖；写入 200ms 合并。
- 轮转 `themes.prev.json` 的前提：主索引存在且能被解析成 `ThemeCatalog`（可读才轮转）。
- 图片导入降采样到最长边 2048；>20MB 或 >6000px 拒绝；字体 ttf/otf ≤10MB。
- 孤儿清理：删除资产走 `pending-delete` 队列，宽限期 24 小时；删除前**重读索引二次核对**引用集，并扫描其余白名单扩展名兜底；只在索引提交成功后清理（见 `ThemeStore.cleanOrphansIfNeeded`）。
- 主题资产**不计入**普通「缓存占用」，需单独统计「主题资产占用」。

## 3. backend 三态与回退开关（全局保险丝）

`ThemeStore.Backend`：`legacy` / `dualWrite` / `themeStore`。默认初始化为 `.legacy`；正常写入走 `requestWrite()` 会切到 `.themeStore`。切换接口：`ThemeStore.shared.switchBackend(_:)`。

- `.legacy`：只用旧逻辑，不动主题存储。**异常时的回退目标，无需重启、不白屏。**
- `.dualWrite`：旧逻辑继续写 + `shadowWrite(catalog:)` 影子写主题存储；对账脚本骨架就位。
- `.themeStore`：主题存储为主。

**对账门禁时点（重要，别踩坑）**：`dualWrite` 对账式「令牌 == 旧 Palette 值」且「activeTheme == ReaderSettings.theme」在 `Palette` 降壳（P1-01）之前**恒真、没有验证力**。因此真实对账门禁**后移到 P1-01 之后**执行（随 G1 验收）；切 `.themeStore` 必须等该门禁通过。当前代码中 `.dualWrite` 只落影子写骨架。

**回退步骤**：
1. 调用 `ThemeStore.shared.switchBackend(.legacy)`（或由集成层把开关切回 legacy）。
2. 确认界面回到旧外观且无白屏、无崩溃。
3. 排查原因后再决定是否切回 `.dualWrite` → `.themeStore`，切回前必须重跑对账门禁。

## 4. 启动加载与损坏兜底链

`ThemeStore.bootstrap()` 同步读取（几十 KB / 几十毫秒，不解码图片字体，不阻塞首帧）。兜底顺序：

1. 读 `themes.json`；不存在则读 `themes.prev.json`（标记 `recoveredFromPrevious = true`）；都没有则用内置默认并立即落盘。
2. 解码成功：`schemaVersion > 当前` → **只读降级**（不写盘、不留档、不覆盖，仅写 `decodeError`）；`< 当前` → 走 `ThemeCatalog.migrate` 串行升级。
3. `refreshBuiltins(...)`：未被用户改过（`builtin && !customized`）的内置主题按 `builtinRevision` 刷新；缺失的内置主题补齐。
4. `activeThemeID` 指向不存在 / 坏主题 → 回退 `builtin.yehang.original`，写 `decodeError`。
5. 整份 catalog 解码失败 → 先**逐主题兜底** `decodeCatalogPerTheme`：好的留下，坏的记入 `skippedThemes`（不连带整库），写 `theme-decode-error.txt`。
6. 逐主题兜底仍失败 → `quarantineCorruptFile` 把坏文件改名留档为 `themes.corrupt-<ts>.json`，写 `theme-decode-error.txt`，再尝试从 `themes.prev.json` 恢复并重写主索引；prev 也失败则用内置默认。

## 5. 诊断与留档

排查主题问题时，按以下三个来源取证：

| 来源 | 位置 / 入口 | 记录内容 |
|---|---|---|
| **`theme-decode-error.txt`** | `Themes/theme-decode-error.txt` | 解码 / 写入失败原因，逐行追加，含 ISO8601 时间戳。由 `ThemeStore.writeDecodeError` 写入，与日志开关无关，**始终记录**。 |
| **`skippedThemes`** | `themes.json` 中 `ThemeCatalog.skippedThemes` | 逐主题兜底时被跳过的坏主题 ID 列表（上限 256）。 |
| **`DiagnosticLog`** | `Application Support/Legado/Logs/diagnostics.json`；UI：设置 → 网络日志（`NetworkDiagnostics.exportText`） | 通用诊断日志（最多 500 条）。阅读页 `rebuild()` 以 `category: "主题"` 记录 `rebuild #N`，可用于判定「纯换色 rebuild = 0 次、换字体族 = 1 次」。**受 `recordLog` 开关控制**，默认不记录（避免把 URL 写入磁盘）；取证前需确认用户已开启日志记录。 |

补充：`ThemeStore.decodeError`（内存）与 `recoveredFromPrevious`（内存标记）是用户可见提示的数据来源，重启后不保留；磁盘证据以上表三个来源为准。

`.yhthm` 导入失败通过 `ThemePackageError.localizedDescription` 返回明确错误（badMagic / tooLarge / bombRatio / bombDeclared / traversal / duplicateEntry / encryptedEntry / unsupportedMethod / symlinkEntry / checksumMismatch / futureVersion / invalidJSON / executableContent），不崩溃。

## 6. 备份与恢复

- 备份范围：主题纳入 `BackupScope.preferences`（「阅读偏好」）。`BackupPayload` 增加 `themeCatalog` + `themeAssets`（资产 base64 内嵌，JSONEncoder 自动处理）。
- 打包（`AppStore.makeBackupPayload`）：勾选 `preferences` 才带主题字段；`themeAssetsForBackup()` 按**原始字节 15MB 上限**控制（base64 后约 +33%，仍 <20MB），超限返回 nil——此时只备 catalog，不备资产。
- 恢复（`AppStore.restore(from:)`）顺序固定：
  1. 遍历 `themeAssets` 调 `ThemeAssetStore.importAsset(...)` 先装资产（没带就跳过）。
  2. `themeCatalog` 存在 → 替换 `ThemeStore.shared.catalog`。
  3. `selectTheme(id: catalog.activeThemeID)` 设当前主题。
  4. 写 `themeSelection`（`activeThemeID` + `catalogSchemaVersion`）。
  5. `flushSnapshot()` + `ThemeStore.shared.flush()` 立即落盘。
- 只覆盖备份**确实带了**的字段，避免半份备份清空数据。恢复后若自定义资产缺失，需用 `.yhthm` 手动补。

## 7. 门禁 tag 与回退步骤

阶段门禁（Gate）与对应 tag，来自实施任务清单：

| 阶段 | 门禁 | tag | 关键内容 |
|---|---|---|---|
| 阶段 0 地基 | G0 | `theme-p0-gate` | 老数据可读、坏文件留档、未来版本只读、影子写就位 |
| 阶段 1 令牌适配 | G1 | `theme-p1-gate` | 全 App 一致换肤、背景零动画、性能达标 + dualWrite 对账 |
| 阶段 2 阅读融合 | G2 | `theme-p2-gate` | 继承/覆盖正确、字号滑块不整树重建、D20 对齐 |
| 阶段 3 编辑器与资产 | G3 | `theme-p3-gate` | 冷启动首帧、ZIP 往返、导入攻击防护、C-3 字体版权三段闭环 |
| 阶段 4 打磨 | G4 | `theme-v1-release` | 全加载态换肤、无障碍与性能门禁、activeThemeID 跨端、合规 A/B 类验收 |
| 二期同步 | G5 | `theme-sync-gate` | 冲突三选项、墓碑删除同步（**二期，未开放**） |

统计口径：`git grep` 一律限定 `YeHangChuan/`，排除 `.claude/worktrees/`；区分「调用点」与「grep 命中行」。

**回退步骤（按粒度从轻到重）**：
1. **运行时回退**：`switchBackend(.legacy)`（见第 3 节），不动代码。
2. **提交级回退**：一任务一原子 commit，用 `git revert <commit>` 逐任务回退；或 `git cherry-pick` 选择性保留。
3. **阶段级回退**：`git diff <上一 tag>..HEAD` 定位阶段改动，整体 revert 到上一门禁 tag（如 `git revert theme-p1-gate..HEAD`），回到最近通过的稳定门禁。
4. **数据回退**：主题数据与代码解耦——回退代码不会损坏主题数据；如需还原主题文件，用 `themes.prev.json` 或备份包 / `.yhthm` 恢复。

## 10. 二期 iCloud 主题同步如何开启（当前未开放）

**状态**：`ThemeSyncService.swift` 已实现 push / pull / tombstone（记录类型 `YeHangThemeCatalog`，每主题一条 CKRecord，`payload` 为 CKAsset + `assets`，按 `assetIDs` 去重，本机优先、`updatedAt/deviceID` 判冲突、墓碑保留 30 天）。**默认关闭，未接入任何开关** —— 当前版本用户不可用。

开启（按架构方案 §10.1 与任务清单 P5 系列）需补齐：

1. **开关**：功能实验室「主题 iCloud 同步」，**默认关闭**；开启时请求 CloudKit 权限，未登录 / 拒绝则关闭同步并如实提示。
2. **接服务**：把 `ThemeSyncService.shared` 的 `push/pull/tombstone` 接到设置 → 主题 → 同步详情的触发链；`pull()` 返回的 `SyncRecord`（新增 / 冲突 / 墓碑）需逐条处理。
3. **冲突解决 UI（P5-04）**：远端 `updatedAt > 本地` 时进入三选一——保留本机（默认）/ 采用远端（校验通过才替换）/ 保留两份（远端改名「原名（来自〈设备名〉）」+ 新 ID 并存）。显示双方修改时间与缩略预览，**不静默覆盖**。
4. **容量与兜底**：单主题 payload <1MB、单资产 <10MB、整主题 <50MB；超限提示改用 `.yhthm`。CloudKit 不可用不影响本机主题。
5. **与一期共存**：一期 `activeThemeID` 仍走现有 Snapshot（`YeHangSnapshot`），二期主题本体走独立记录，两者互不冲突。
6. **门禁**：完成后跑 G5（`theme-sync-gate`）——构造时间戳冲突验证三选项、删除后另一端同步删除且不回传。

> 一期 `activeThemeID` 同步的触发链（`Models.swift` 中 apply 后把 ID 应用到 ThemeStore、本机无此 ID → 回退默认 + 提示）**已归一期并实现**，与二期解耦，不要混用记录类型。
